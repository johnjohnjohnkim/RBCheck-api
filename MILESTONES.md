# Milestones: RBCheck (backend) + RBCheck-client

Goal: make RBCheck hostable on AWS and give it TD-style daily spending insights. The MacBook keeps reading iMessage and pushes parsed transactions over HTTPS to the API in AWS; Postgres lives next to the API in AWS; the static client reads from the API.
Out of scope: iPhone Shortcuts ingestion (parked), Alembic migrations (unless a change is unavoidable), public sign-up / multi-user accounts, email or push notifications for insights.

Repos: backend `D:\repos\RBCheck` (this file lives here), client `D:\repos\RBCheck-client`. Milestones may touch both.

## Loop rules
- Work one milestone at a time, in order.
- A milestone is done only when its done-check passes. Run it and show the output.
- Before committing, run the review loop: spawn a reviewer subagent on the milestone's diff (bugs, security, simpler or more efficient design). Fix what it finds, then re-run the reviewer. Repeat until both the reviewer and I are satisfied. Record the rounds in the report.
- Then: run the `/journal` skill for the milestone, commit in each repo that changed, and push to the feature branch `milestones` (never to `main`, never force-push). `gh` is not installed, so no PRs; the user opens them.
- Commits: no attribution trailers other than what the harness says. Never commit `.env`, `*.db`, `venv/`, or anything with credentials.
- After the commit, tick the box, fill in the report, send a push notification, and continue to the next milestone unless it lists a blocker.
- A milestone with a **Blocker** stops the loop. Notify the user with what is needed. Don't work around it.
- If a done-check can't pass after a reasonable effort, STOP and notify with what was tried. Don't weaken the check.
- Never run anything that creates, changes or deletes AWS resources, touches IAM, or spends money without the user's explicit go-ahead in the current conversation. Never write secrets to files in the repo.
- Never delete outside the project. Never touch the user's real Postgres data.
- Do not edit this file's goals or checks. Only tick boxes and fill in reports.

## 2. Daily insights: backend  [x]
Why: the main feature. RBC gives no daily view; this computes one.
Touches: `app/models.py` (new `daily_digest` table, created by `create_all`), `app/services/insights.py`, `app/routers/insights.py`, `app/main.py`, `app/config.py` (new `TIMEZONE`, default `America/Toronto`), `app/scripts/digest.py`, `app/routers/transactions.py` (summary and "today" endpoints use the configured timezone), `tests/`.
What it computes per day: spend today, 7-day average and percent difference, top 3 merchants, month-to-date total with projected month-end, unusually large charges (e.g. over 2x the merchant or overall median), count of transactions. Spend excludes Deposit and Credit Card Payment, and Credit Refund subtracts, same as the client.
Endpoints: `GET /insights/today` (computes and stores if missing), `GET /insights/history?days=30`.
Blockers: none
Done-check: `venv\Scripts\python.exe -m pytest -q` -> all pass, including new tests that cover the digest math on fixed data, the timezone boundary (a purchase at 11:30pm Toronto time counts on that day even when the server clock is UTC), idempotent re-computation, and both endpoints.
Report: Digest service, `daily_digests` table, `/insights/today` and `/insights/history`, `app/scripts/digest.py` (default last 2 days), `TIMEZONE` setting (validated at startup; Postgres session timezone set; ingestion now stamps messages with an explicit zone from UTC seconds), one shared spending definition used by the summary and digests, rolling-7-days now means seven days including today. Two reviewer rounds: round 1 found stale cached digests, the session-timezone data shift, a first-save race, N+1 queries, payload drift and a distorted projection; all fixed (digests are reused only once `settled`, i.e. final, 2h past day end, and current `v`; projection is null until 3 completed days). 56 tests pass. NOT verified on real Postgres (Docker Desktop was not running); revisit in milestone 6. Before deploying against the existing database run `SHOW timezone;` and follow the README section 'Upgrading an existing database (timezone)'. Deferred: merchant-name normalisation, early-history dilution, projection skew in the first month. Journal: `journal/2026-10-09-daily-insights-backend.md`.

## 4. Auth and Mac push ingestion  [x]
Why: once hosted, the API is on the internet and the Mac must send to it.
Touches: `app/config.py` (`WRITE_TOKEN`, `READ_TOKEN`, both required in production), `app/auth.py`, routers (writes need the write token, reads need a read token), `app/routers/ingest.py` (`GET /ingest/cursor`, `POST /ingest/batch`), `app/scripts/poller.py` and `app/scripts/backfill.py` (push over HTTPS using `RBCHECK_API_URL` and the write token instead of writing to Postgres directly), `tests/`.
Rules: tokens compared with `hmac.compare_digest`; missing or wrong token gives 401; `/docs` and the OpenAPI schema are disabled unless a debug flag is set; CORS allows only the configured site origin, not a regex.
Blockers: none
Done-check: `venv\Scripts\python.exe -m pytest -q` -> all pass, including tests that: a request without a token is 401 on every route; a read token cannot write; the poller against a fake HTTP API sends new messages once, resumes from the server cursor after a restart, and survives the server being down (retries, cursor unchanged).
Report: Bearer-token auth (READ_TOKEN / WRITE_TOKEN, both required, hmac.compare_digest; reads accept either, writes need the write token; 401 none/invalid, 403 read token on a write route), docs disabled by default, explicit CORS origins (validated, no wildcard), 1 MB body limit, `/healthz`. New `/ingest/cursor` and `/ingest/batch` with per-record validation; the Mac poller/backfill now push over HTTPS (`app/scripts/pusher.py`, imports nothing from app.config/app.database) with resume-from-server-cursor, exponential backoff (cap 300s), catch-all resilience, https-only URL, reset warning. Dedupe is now one-to-one and atomic (payment insert and withdrawal deletion in one transaction; manual entries never touched). Two review rounds: round 1 found no auth bypass but real robustness issues (poller dying on unexpected errors, greedy dedupe, poison-pill 500s, no body limit), all fixed; round 2 found nothing High/Medium, low items fixed or documented. 124 tests pass; breaking the auth check or the rollback on purpose makes tests fail. NOT verified: real Postgres (ingest tests run on SQLite), a live Mac chat.db; the client sends no token until milestone 5. Journal: `journal/2026-10-09-auth-and-mac-push-ingestion.md`.
